## Threat Model

| Threat Type | Scenario | Potential Impact |
|-------------|----------|------------------|
| Spoofing | An attacker uses stolen staff credentials against a login path where MFA is optional or not enforced, such as an alternate LDAP-backed login. Alternatively, the attacker steals an authenticated PHP session through a vulnerable page or compromised browser and impersonates the clinician without repeating MFA. | Unauthorized access to PHI and the ability to enter clinical notes, initiate prescription workflows, or change patient information under the clinician's identity. |
| Spoofing | An attacker abuses insufficient identity verification during Patient Portal self-registration or an inadequately bound e-mail password-reset flow to associate an attacker-controlled account with an existing patient's chart. Compromise of the patient's e-mail account could also enable takeover if recovery relies solely on e-mail. | Disclosure of patient records and lab results, fraudulent patient messages, and unauthorized changes to appointments or patient-submitted information. |
| Spoofing | A malicious application uses dynamic OAuth client registration to imitate a trusted SMART on FHIR application. If redirect URI validation or authorization-response binding is incomplete, it could obtain authorization codes or tokens. Separately, theft of a system client's JWT signing key could let an attacker impersonate an integration with bulk-access permissions. | Unauthorized API access under a legitimate user or integration identity, potentially including large-scale extraction of FHIR patient records. |
| Spoofing | An attacker impersonates an external laboratory, clearinghouse, or payment provider using stolen integration credentials or a connection whose peer identity is not adequately verified. The attacker submits fabricated HL7 results, X12 remittances, or payment notifications as though they originated from the trusted provider. | False clinical results, incorrect account balances, disrupted revenue collection, and treatment decisions based on fraudulent information. |
| Tampering | An attacker supplies crafted input to a legacy PHP search, reporting, billing, or API endpoint containing an SQL injection flaw. If the query runs with write privileges, the attacker modifies allergies, medications, encounter records, insurance details, or billing entries in MySQL/MariaDB. | Corrupted clinical and financial records, unsafe treatment decisions, fraudulent claims, and costly reconstruction of trustworthy patient histories. |
| Tampering | An attacker places stored script content in a clinical form, patient message, demographic field, or imported document metadata that is later rendered without adequate output encoding. The script executes in a staff browser and submits record-changing requests. A separate state-changing endpoint with missing CSRF validation could allow similar changes through a malicious external page. | Unauthorized modification of clinical notes, scheduling, billing, or administrative settings using the victim's permissions; stored XSS may also read accessible anti-CSRF tokens. |
| Tampering | A user exploits path traversal or an insufficiently constrained filename in document upload, import, or restore functionality to overwrite another patient's files under sites/<site>/documents. If filesystem permissions allow broader writes, the same weakness could alter site configuration, queued integration files, or backup contents. | Replacement or destruction of medical evidence, altered application behavior, contamination of restored records, and possible effects on other sites sharing the server. |
| Tampering | A compromised laboratory or clearinghouse account submits altered or replayed HL7/X12 files, or modifies files in a shared staging directory before a cron job imports them. If import processing does not establish message integrity, uniqueness, and correct patient or encounter linkage, the altered data is accepted as authoritative. | Incorrect lab values, misfiled results, duplicate remittance postings, and inaccurate clinical or financial records despite otherwise encrypted transport. |
| Repudiation | A database administrator or attacker with application database credentials changes or deletes PHI-access audit entries stored alongside operational records. Where optional tamper-evident checksums are disabled, or their integrity material is accessible to the same attacker, the altered history may not be distinguishable from legitimate logs. | Inability to reliably establish who accessed or changed records, weakened incident investigations, and reduced evidentiary value for regulatory or legal proceedings. |
| Repudiation | Staff share accounts, or an unattended authenticated workstation is used by another person. Clinical notes, prescription requests, billing edits, and document downloads are attributed only to the account holder, who subsequently disputes performing them. | Unreliable attribution of clinically significant actions, difficulty resolving malpractice or fraud disputes, and reduced accountability for inappropriate PHI access. |
| Repudiation | A third-party application performs changes through OAuth APIs or a background job imports HL7/X12 records, but logs do not preserve the client identity, initiating user where applicable, site, source message identifier, and resulting record changes. The integration provider and clinic then dispute which party caused an erroneous update or export. | Incomplete end-to-end traceability, inability to distinguish user actions from automated processing, and slower investigation of unauthorized disclosures or corrupted records. |
| Repudiation | An administrator installs a module, changes ACLs, restores a backup, or edits sqlconf.php through SSH, but host activity and web administration events are not correlated with application audit records. Unsynchronized timestamps or log loss during rotation further obscure the sequence of events. | Privileged actors can dispute responsibility for security-sensitive changes, and investigators may be unable to reconstruct how access or application behavior changed. |
| Information Disclosure | A patient, staff member, or API client changes a patient identifier, FHIR resource reference, document identifier, or site selector in a request. If authorization checks only section access or OAuth scope rather than the requested patient and site, the application returns another patient's records or another practice's data. | Cross-patient or cross-site PHI exposure, potentially extending from individual records to entire practice datasets through search or export endpoints. |
| Information Disclosure | A web-server mapping exposes files under sites/<site>/documents directly, bypassing application authorization. Alternatively, a path traversal flaw or exposed configuration copy reveals sqlconf.php, or a publicly reachable backup exposes database dumps and documents. | Disclosure of scanned records, clinical documents, credentials, and historical PHI. Exposed database credentials could enable broader compromise where database connectivity is available. |
| Information Disclosure | A Bulk FHIR export produces files or download URLs whose authorization is weaker than that of the export request, or an offsite backup is accessible to unintended cloud identities. A stolen storage snapshot or backup also reveals PHI if encryption is absent or its keys are available with the copied data. | High-volume disclosure of patient histories, billing information, and other highly sensitive data from a single export, backup, or storage compromise. |
| Information Disclosure | Reminder templates, fax routing, Direct messages, telehealth links, or diagnostic/API logs include more PHI or credentials than intended. Incorrect recipient mappings or excessive provider-side access expose this information. Networked database connections or SMTP hops could also reveal sensitive content if transport protection is absent. | PHI disclosure to incorrect recipients, integration vendors, log readers, or network observers; leaked tokens or telehealth links may enable further unauthorized access. |
| Denial of Service | An Internet attacker repeatedly invokes expensive FHIR searches, Bulk FHIR exports, CQM reports, or document conversions. Without effective request, concurrency, and workload limits, these operations exhaust PHP-FPM workers, database connections, CPU, memory, or temporary disk space. | Clinical staff and patients cannot access records, scheduling, or prescribing workflows when needed, including during time-critical care. |
| Denial of Service | An authenticated portal user or compromised integration submits oversized files, highly compressed archives, or malformed CCDA/HL7 input to upload and import pipelines. Resource-intensive parsing or repeated retries consume storage and processing capacity, while a poison message may block subsequent queued work. | Unavailable document services, delayed lab results, growing integration backlogs, and possible interruption of the application or database when shared storage fills. |
| Denial of Service | An attacker gains code execution through a vulnerable legacy PHP component or installed module and encrypts or deletes the database and documents. Backups mounted with the same writable credentials are also damaged, and shared runtime permissions allow the attack to affect multiple sites. | Extended EHR outage, loss of clinical history, cancellation or diversion of care, and inability to recover promptly from ransomware. |
| Denial of Service | A laboratory, clearinghouse, e-prescribing service, or notification provider becomes unavailable or returns slow responses. If OpenEMR performs blocking calls or background jobs retry without bounds, requests and jobs accumulate, consuming worker capacity and delaying unrelated workflows. | Delayed prescriptions, lab processing, claims, and reminders, with cascading application outages if external-service failures exhaust shared resources. |
| Elevation of Privilege | A patient or low-privilege staff member directly invokes an administrative PHP handler or API operation that relies on hidden UI controls rather than server-side phpGACL and object-level checks. An analogous OAuth scope-mapping error grants a patient application staff-only write operations. | Unauthorized ACL changes, user administration, global configuration changes, or access to privileged clinical and financial functions. |
| Elevation of Privilege | An attacker reaches setup.php or sql_upgrade.php after deployment. If these scripts do not require appropriate installation state and authorization, the attacker uses their database or configuration privileges to change the installation, create privileged access where supported, or execute unintended schema operations. | Administrative takeover or destructive database changes through functionality intended only for installation and maintenance. |
| Elevation of Privilege | A malicious third-party module is installed through the admin UI, or an attacker exploits an upload flaw that places executable PHP in a web-executable directory. The resulting code runs with application privileges, bypassing role checks and accessing sqlconf.php, integration secrets, and other sites where filesystem permissions permit. | Full application compromise, database and document access, manipulation of external integrations, and potential cross-site compromise from one extension or upload path. |
| Elevation of Privilege | After obtaining execution as the web-service account, an attacker modifies an application-writable backup or synchronization script that a more privileged cron job executes. Excessive container privileges, accessible host mounts, or writable service configuration could provide additional routes from application access to host-level control. | Host takeover, compromise of all practices on the server, theft of offsite-backup or SSH credentials, and persistence outside the application's authorization and audit controls. |


## Improvement Suggestions

- Provide the exact OpenEMR release, PHP version, database version, installed modules, dependency versions, and patch status. The description identifies legacy technologies but does not establish which vulnerabilities apply to this deployment.
- Clarify whether 'Top Secret' is an internal sensitivity label or a formal classification, identify the affected data, and describe how that classification relates to the PHI and regulatory requirements listed.
- Resolve the MFA ambiguity: the application metadata lists MFA, while the description makes it optional. Identify enforcement for staff, administrators, patients, LDAP users, APIs, SSH access, and account recovery.
- Provide deployment and network diagrams showing TLS termination, reverse proxies, reachable ports, database placement, container or VM boundaries, management access, and trust zones between components.
- Describe login, session, and recovery flows, including cookie settings, session rotation and expiration, MFA enrollment and reset, portal identity verification, and patient-account-to-chart linkage.
- Provide OAuth/OIDC configuration and flows, including dynamic registration rules, redirect URI handling, JWT validation and key custody, refresh-token behavior, SMART launch context, consent, and scope-to-permission mappings.
- Provide the role and permission matrix and examples of server-side authorization for patients, encounters, documents, administrative actions, and REST/FHIR operations, including any emergency-access exceptions.
- Explain how a request selects a site and how sites are isolated through database accounts, sessions, filesystem permissions, application processes, and background-job credentials.
- Describe document upload, CCDA/XML parsing, HL7/X12 import, archive extraction, and export pipelines, including accepted formats, staging directories, execution permissions, patient matching, and message replay handling.
- Provide external-integration data-flow details: transport and peer authentication, credential ownership, inbound notification validation, exchanged fields, provider retention, timeouts, retries, and queue behavior.
- Describe encryption and key management for databases, documents, logs, exports, backups, and networked connections, including which application, administrator, and provider identities can access plaintext or keys.
- Provide audit event coverage, recorded identity and correlation fields, checksum design and key storage, log access permissions, retention, timestamp synchronization, and coverage of SSH, module installation, restores, and configuration changes.
- Describe module installation and update provenance, who can install extensions, whether modules are isolated, and the post-installation accessibility and authorization behavior of setup.php and sql_upgrade.php.
- Provide availability and recovery details, including resource limits for reporting and Bulk FHIR export, job isolation, database capacity, backup destinations and permissions, restore dependencies, and required recovery time and recovery point objectives.
- Describe host and container privilege boundaries, service accounts, writable mounts, cron execution identities, SSH administration paths, and whether maintenance scripts are writable by the web application.
