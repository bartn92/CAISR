| Threat Type | Scenario | Suggested Mitigation(s) |
|---|---|---|
| Spoofing | Stolen staff credentials bypass optional MFA through alternate LDAP login, or a stolen PHP session impersonates a clinician. | **Enforce MFA on every staff authentication path**, including LDAP-backed and fallback logins; disable paths that cannot enforce equivalent controls. Prefer phishing-resistant WebAuthn/FIDO2. Regenerate PHP session IDs after authentication and privilege changes; use strict session handling and `Secure`, `HttpOnly`, and appropriate `SameSite` cookies. Apply idle and absolute session limits, server-side logout/revocation, and revocation after suspected compromise. Require fresh authentication for sensitive prescribing or account changes. Address XSS and managed-browser security: MFA alone does not protect a stolen authenticated session. |
| Spoofing | Weak portal registration or e-mail recovery lets an attacker link an account to an existing patient chart. | Bind chart enrollment to a **single-use, short-lived invitation issued after patient identity verification**, rather than matching publicly available demographics alone. Verify proxies and guardians separately and explicitly authorize their chart access. Bind reset tokens to the intended account and recovery purpose; make them unpredictable, expiring, and single-use. Require an additional verified factor or an identity-proofed assisted process for high-risk recovery and chart relinking. Notify existing verified contacts of recovery/contact changes and revoke existing sessions after recovery. Rate-limit enrollment and recovery attempts. |
| Spoofing | A malicious SMART on FHIR client imitates a trusted application, intercepts authorization responses, or uses a stolen system-client signing key. | Treat dynamic registration as **untrusted onboarding**, not approval for privileged scopes; verify publishers and explicitly approve bulk-access clients. Require exact registered redirect-URI matching, disallow wildcards/open redirects, and enforce authorization-code flow with PKCE S256 and response-to-session binding; validate issuer and OIDC nonce where applicable. Bind codes to client, redirect URI, and PKCE challenge. For system JWT authentication, validate signature, algorithm, issuer/subject, audience, expiry, and replay-resistant `jti`. Protect signing keys in a KMS/HSM where feasible, rotate/revoke them, and grant narrowly scoped access. |
| Spoofing | An attacker impersonates a laboratory, clearinghouse, or payment provider and submits fabricated transactions. | Give each partner and environment distinct, least-privilege credentials; store them in a secrets manager and rotate/revoke them promptly. Verify TLS certificates and hostnames, pin SFTP host keys through a controlled process, and use mTLS where supported. Authenticate payment webhooks with provider-supported signatures covering the exact payload, timestamps, and replay identifiers. Bind HL7/X12 sender identifiers to the authenticated partner rather than trusting message headers. Reconcile payment notifications against authenticated provider transaction records before posting balances. Use network allowlists only as a supplementary control. |
| Tampering | SQL injection in legacy PHP endpoints modifies clinical or financial records in MySQL/MariaDB. | Replace concatenated SQL with **parameterized queries across legacy search, reports, billing, and API code**; allowlist dynamic identifiers such as sort columns that cannot be parameterized. Assign read-only database identities to reporting/search workloads where practicable and remove runtime DDL, `FILE`, and unnecessary write privileges. Patch affected components and add injection-focused code review, SAST/DAST, and regression tests. Use a WAF only as an interim defense. Preserve protected record-change histories and tested backups to investigate and recover corrupted data. |
| Tampering | Stored XSS or missing CSRF checks cause record-changing requests from staff browsers. | Apply context-appropriate output encoding to clinical forms, messages, demographics, and imported metadata; sanitize permitted rich text with a maintained allowlist sanitizer. Avoid unsafe DOM sinks and deploy a nonce/hash-based CSP as defense in depth. Require validated, session-bound CSRF tokens on cookie-authenticated state changes; prohibit mutations through GET and check request origins. Use `SameSite` cookies as an additional defense. **Fix XSS independently:** scripts executing in the application origin can often use CSRF tokens. Require fresh authentication for especially sensitive administrative changes. |
| Tampering | Path traversal or unsafe filenames overwrite patient documents, configuration, staging files, or backups. | Generate server-side storage names and derive patient/site destinations from authorized server-side context, not supplied paths. Reject absolute paths and traversal; enforce resolved-path containment and use safe filesystem operations that prevent symlink and check/use races. Store uploads outside executable web paths and separate each site's writable document area. Make configuration, code, and backup repositories non-writable by the upload service. Run restore/import operations through a restricted maintenance identity, validate archive entries before extraction, and retain protected document versions and integrity metadata. |
| Tampering | Altered or replayed HL7/X12 messages, including staging-directory modifications, are imported as authoritative data. | Authenticate the sender and verify message signatures/MACs or authenticated manifests where supported; encryption in transit alone does not protect staging files. Separate partner staging directories, restrict write access, and atomically move accepted files into an importer-controlled, non-modifiable queue. Track message/control identifiers with sender and site context; enforce idempotent posting and defined correction/replay handling. Validate schemas, patient identifiers, encounter linkage, and transaction consistency; quarantine ambiguous matches. Retain original payloads and provenance. Reconcile suspicious results or remittances independently, since a compromised legitimate sender may produce valid signatures. |
| Repudiation | Database administrators or stolen database credentials alter PHI-access audit history and its integrity material. | Stream audit events promptly to an **independently administered, append-only or retention-locked log store** inaccessible to application/database administrators for modification. Use an insert-only application logging identity where supported. Enable tamper-evident logging, with signing/HMAC keys held outside the operational database and anchored integrity checkpoints stored externally. Audit privileged database activity through a separately protected collection path. Monitor collection failures, sequence gaps, deletion attempts, and integrity-verification failures; periodically test verification and retention. Checksums stored with mutable logs are insufficient on their own. |
| Repudiation | Shared accounts or unattended workstations make clinical and financial actions difficult to attribute. | Require unique accounts, prohibit shared interactive credentials, and provide individually attributable emergency-access accounts with review. Use rapid individual sign-in, such as badge-assisted SSO with appropriate authentication, to reduce pressure to share sessions. Enforce workstation locking and application idle limits, including on shared clinical terminals. Require fresh authentication and explicit confirmation for high-risk actions; apply applicable electronic-prescribing signing requirements. Record actor, session, workstation, patient, action, and timestamp in protected audit logs. Treat account attribution as evidence, not definitive proof of which person used an unattended session. |
| Repudiation | OAuth applications and HL7/X12 imports lack end-to-end identity and change provenance. | Log the OAuth `client_id`, authenticated user when present, service identity for autonomous jobs, authorized scopes, site, target records, action, and outcome. For imports, retain sender identity, source message/control identifier, payload digest, importer version, and resulting record identifiers or protected change history. Generate correlation IDs at trusted entry points and propagate them through queues and downstream calls. Preserve export manifests and delivery/access events. Keep logs tamper-resistant and time-synchronized; exclude tokens and unnecessary PHI. Define partner traceability and retention requirements contractually. |
| Repudiation | SSH and web administrative changes are not correlated, or clock drift and rotation destroy the event sequence. | Use named administrative identities, MFA-protected privileged access, and attributable `sudo` rather than shared root access. Centrally collect SSH, privilege-escalation, host audit, web-admin, deployment, ACL, restore, and module-install events. Monitor changes to `sqlconf.php`, executable code, cron definitions, and security configuration without copying secrets into logs. Correlate events using administrator identity, host/site, session, and change-ticket identifiers. Synchronize clocks using controlled time sources, monitor drift, and test log shipping, rotation, buffering, retention, and loss alerts. |
| Information Disclosure | Identifier manipulation exposes another patient's records or another site's data despite section access or OAuth scope checks. | Enforce **server-side object- and tenant-level authorization on every request**, binding the user/client to the requested patient, site, and resource relationship. Derive site context from trusted identity/session configuration rather than an unchecked selector. Treat OAuth scopes as an upper bound, not proof of patient authorization. Apply the same restrictions to FHIR search, references, `_include`, history, documents, and bulk exports; constrain queries before returning results or counts. Add cross-patient/cross-site negative tests and isolate tenant databases/storage where feasible. Unpredictable identifiers are only supplementary protection. |
| Information Disclosure | Direct document serving, traversal, exposed `sqlconf.php` copies, or public backups disclose PHI and credentials. | Move documents, configuration, and backups outside the web root. Serve documents only through an authorized application handler or an internal web-server redirect issued after authorization; block public aliases to `sites/<site>/documents`. Deny access to configuration, dump, archive, editor-backup, and hidden files; disable directory indexing and test actual deployed mappings. Fix traversal and restrict filesystem permissions. Scan deployments and storage for accidental exposure. If configuration was exposed, rotate credentials, investigate access, and restrict database connectivity to approved application hosts. |
| Information Disclosure | Bulk FHIR download files or offsite backups have weaker access controls; stolen snapshots reveal unencrypted PHI. | Apply the export request's client/site authorization to job status, manifests, and every file download. Prefer authenticated downloads; where signed URLs are used, treat them as bearer secrets, make them short-lived and narrowly scoped, and exclude them from logs. Use private storage, public-access prevention, least-privilege cloud IAM, and access monitoring. Encrypt exports, backups, and snapshots using separately controlled KMS keys; restrict both ciphertext access and key-decryption permissions. Enforce export expiry/deletion, audit downloads, and test backup access and recovery controls. |
| Information Disclosure | Notifications, fax/Direct routing, telehealth links, logs, database connections, or SMTP disclose excessive sensitive data. | Minimize reminder content and direct patients to an authenticated portal for details. Verify recipient mappings and contact changes; validate fax destinations and Direct identities, and use confirmation for sensitive transmissions. Make telehealth links short-lived and require appropriate participant authentication or admission controls. Redact PHI, credentials, tokens, and URLs carrying secrets from diagnostic logs; restrict access and retention. Require certificate-validated TLS for remote database connections and integration transport. For sensitive e-mail, use secure messaging/Direct or fail-closed protected delivery rather than relying on opportunistic SMTP TLS. Restrict vendor access and establish applicable privacy agreements. |
| Denial of Service | Expensive FHIR searches, exports, reports, and conversions exhaust application and database resources. | Apply layered per-client, user, site, and IP rate limits, plus global capacity safeguards. Bound FHIR page sizes, query complexity, search time, and export frequency. Queue reports, conversions, and exports asynchronously with concurrency caps, cancellation, and per-site quotas. Isolate those workers and database connection pools from interactive clinical workloads. Set PHP-FPM, database statement, memory, temporary-storage, and execution limits; optimize/index expensive queries. Load-test limits and alert on queue age, worker saturation, and disk pressure. Return controlled `429`/`503` responses rather than accepting unlimited work. |
| Denial of Service | Oversized uploads, decompression bombs, malformed CCDA/HL7, and poison messages exhaust or block import pipelines. | Enforce upload limits at the proxy and application, including **decompressed size**, archive entry count, nesting, and expansion ratio. Disable XML external entities and DTD processing for CCDA; limit parser depth, fields, memory, CPU, and execution time. Parse in isolated workers with bounded temporary storage and no unnecessary network access. Use per-partner/site quotas, bounded retries, and dead-letter queues so poison messages cannot block later work. Separate staging storage from database/system volumes; monitor capacity and securely expire abandoned uploads. |
| Denial of Service | Exploited PHP components or modules enable ransomware that destroys databases, documents, and shared writable backups. | Maintain supported PHP/application/module versions, remove unused components, and restrict administrative access. Run immutable or read-only application code with least-privilege database and filesystem access; isolate sites using distinct service identities and storage boundaries. Maintain encrypted, immutable/offline backups under credentials unavailable to the web runtime, including document versions and database point-in-time recovery. Test restoration against clinical recovery-time and recovery-point objectives. Monitor destructive file/database activity, restrict unnecessary outbound access, and maintain rehearsed containment and clinical downtime procedures. |
| Denial of Service | Slow or unavailable external providers cause blocking requests and unbounded retries that disrupt unrelated workflows. | Set connection, read, and overall deadlines on every provider call. Use circuit breakers, bounded queues, and exponential-backoff retries with jitter and retry budgets. Isolate workers and connection pools by integration so one provider cannot exhaust clinical capacity. Make retries idempotent and reconcile uncertain outcomes before resubmitting prescriptions, claims, or payments. Prefer asynchronous processing where clinically appropriate, with clear pending/failed states rather than false success. Monitor provider latency and queue age; define safe downtime and manual-reconciliation procedures with clinical and operational owners. |
| Elevation of Privilege | Direct administrative handler access or incorrect OAuth scope mapping gives low-privilege users staff/admin operations. | Require centralized, deny-by-default authorization in **every PHP handler and API operation**, independent of UI visibility. Enforce phpGACL permissions, site/patient object checks, and function-specific privileges before side effects. Map SMART scopes explicitly to permitted operations and intersect them with user role, patient context, and client approval; patient scopes must never imply staff administration. Separate service-client and interactive-user permission models. Test each privileged route using anonymous, patient, low-privilege staff, and cross-site identities; audit denied attempts and privilege changes. |
| Elevation of Privilege | Exposed `setup.php` or `sql_upgrade.php` permits unauthorized installation or schema changes. | Remove installation/upgrade scripts from production images where feasible, or deny web access by default at the web-server/reverse-proxy layer. Enable maintenance only through a controlled, time-limited process requiring authenticated privileged operators and installation-state checks. Prefer restricted CLI or management-network execution. Use a separate temporary migration database identity; ordinary application credentials should not have schema-administration privileges. Protect maintenance requests against CSRF where applicable, record operations, verify script exposure after deployment, and revoke migration credentials and restore access restrictions immediately afterward. |
| Elevation of Privilege | A malicious module or executable upload runs with application privileges and compromises secrets or other sites. | Restrict module installation to dedicated, strongly authenticated administrators with change approval; review module source, provenance, dependencies, and publisher signatures where available. Deploy approved modules through controlled CI/CD, keeping production code non-writable by the web account. Store uploads outside web-executable directories and explicitly disable PHP/script handling there; extension checks and filesystem `noexec` alone do not prevent PHP interpretation. Validate file types and scan uploads. Use separate per-site runtime identities and secret/database permissions. Recognize that an in-process PHP module effectively shares the application's privileges. |
| Elevation of Privilege | Writable privileged cron scripts, host mounts, or container configuration allow escalation from web-service execution to host control. | Make privileged scripts, cron entries, service definitions, and **all parent directories and sourced configuration** owned by administrators and non-writable by application identities. Use fixed absolute paths and controlled environments; never execute uploaded/generated content. Run backup/synchronization jobs under dedicated least-privilege accounts, exposing no backup or SSH credentials to the web runtime. Run containers as non-root, drop unnecessary capabilities, enable `no-new-privileges`, and apply seccomp/AppArmor/SELinux controls. Avoid privileged containers, container-runtime sockets, and writable sensitive host mounts; monitor privileged configuration integrity and patch hosts. |
